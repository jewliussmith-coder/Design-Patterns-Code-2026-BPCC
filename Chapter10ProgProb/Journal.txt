Journal:

Phase 1: Writing this program was pretty simple, but I noticed I had to use 4 conditional branches to check the guard's current state. If I added a new state, like Sleeping or Panicked, I would have to go back and edit at least 2 methods: hearNoise() and loseTarget(). This could make the code more complicated and harder to manage as more states are added.

Phase 2: The context ,SentinelGuard, is responsible for keeping track of the current state and passing actions to it. The state objects handle what happens depending on which state the guard is in. Delegating to objects is cleaner because I don't have to use a bunch of if/else statements to check the current state. If I want to add a new state, I can create another class instead of changing all the existing methods. This makes the code easier to organize and manage.

Phase 3: This phase demonstrates the Open/Closed Principle because I was able to add a new state without changing the existing state classes. I created the SleepingState class and updated the SentinelGuard constructor to start in that state. The IdleState, PatrollingState, and AttackingState classes remained completely untouched. This makes the program easier to expand without messing up code that already works.

Phase 4: In Phase 1, I had to use multiple if/else statements to manage the guard's behavior, which made the code harder to update when adding new states. By Phase 4, the State Pattern made it easier to add new states without changing the existing ones. I think the State Pattern is more extensible for a professional project because it keeps the code organized and easier to maintain. It also made the logic easier to follow because each state has its own class and responsibilities.
