For Phase 1,
I set up the basic structure of the Composite Pattern by making the InventoryComponent base class, the Item class, and a driver class to test everything out. InventoryComponent holds all the main methods like add(), remove(), getWeight(), and displayInfo(), and Item overrides the ones it actually needs to handle single items with a name and a weight.

Instead of making all the methods abstract, InventoryComponent has default methods that throw an UnsupportedOperationException. This keeps leaf classes like Item from having to write useless code for container methods they do not use, and it lets the main program treat items and containers the exact same way without needing extra checks.


For Phase 2,
I built the Bag class which extends InventoryComponent to act as a container holding other items or bags. I gave it a name, a base weight, and a parameterized list of inventory components, along with methods for adding, removing, getting children, and recursively calculating total weight and displaying info.

In an Item, getWeight just returns the set weight of that single item since it is a leaf. In a Bag, getWeight starts with its own base weight and loops through all its child components, calling getWeight on each one to add them up. Thanks to polymorphism and recursion, the bag treats every child as an InventoryComponent interface without needing to check if it is an Item or another Bag using instanceof, allowing it to handle any level of nesting automatically.

Phase 3
What did you accomplish in this phase? 
 For Phase 3, I put the whole inventory system together by making a main backpack at the root, adding some loose items, and nesting sub-bags inside like a potion pouch and a bag of holding with a gem bag inside that. I tested out printing everything and checking the total weights for both the whole backpack and individual pouches, and I added a try-catch block to handle the error when you try to add an item to a leaf.

If a game designer asks you to add a new container type like a magical WeightlessBag whose contents contribute no weight, what classes would you need to modify, and what classes would remain untouched?
 If we needed a WeightlessBag, I would only have to create a new class for it and change the getWeight method so it only returns its own base weight. Every other class, like the base component, items, regular bags, and the main file, would stay completely untouched.

How does the Composite pattern support the Open/Closed Principle here?

 This proves the Composite pattern supports the Open/Closed Principle because the system is open for adding new features like custom bags, but closed for modification since you never have to rewrite the existing code to get it to work


Phase 4
What bugs or edge cases did you encounter while testing (such as empty bags or calculating total weights)? 
 While testing, I checked an empty bag with nothing inside, and it correctly gave just the base weight without crashing or causing any errors. Removing items from a bag also properly updated the total weight. The recursive loop handles empty components automatically because looping through an empty list just skips straight to returning the base weight.

If you consulted an AI tutor, what feedback or suggestions did it provide, and did you choose to make any changes? Explain your reasoning. 
 I checked with an AI tutor to review the code, and it confirmed that delegating the weight and display methods through the base class without type checks was the right way to do it. It suggested adding custom indentation for deeply nested items to make the text output look cleaner, but I decided not to change it because the simple prefix approach was enough for what the assignment asked for.
